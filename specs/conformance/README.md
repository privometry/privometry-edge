# Conformance vectors

Files both engines must agree on. The Go tests in `specs/` run them against cedar-go; the platform repo runs the same files against the Java bindings.

## policy-verdicts

`privometry.verdicttest/v1` files: compiled Cedar plus requests and the verdicts they must produce.

| Field | Meaning |
|---|---|
| `policies` | Enforce policy set, relative to the vector file |
| `monitor_policies` | Optional monitor set; its result is `would_verdict` and it never uses `unmatched` |
| `unmatched` | `auto`, `allow` or `ask`; `auto` allows risk 0–1 and asks above |
| `tests[].request` | `agent` (product, version, pattern), exactly one of `repo` or `machine: true`, `action`, and `facts` |
| `tests[].expect` | `verdict`, `rule_ids`, and for monitor files `would_verdict`, `would_rule_ids` |

Facts left out take their empty value (`""`, `[]`, risk `none`, `false`), matching what the extractors send. `risk` is written as a level name and converted to 0–4.

Verdict mapping (Contracts v1): a satisfied `forbid` gives `deny`; otherwise an allow decision gives `ask` if any satisfied `permit` is annotated `@verdict("ask")`, else `allow`; when nothing is satisfied, `unmatched` decides. `rule_ids` are the `@id`s of the satisfied policies with the winning verdict.

## policy-compile

For each `policy/v1/examples/valid/<name>.yaml`, the Cedar the Go compiler makes when the file is loaded as the organization layer: `<name>.cedar` (enforce set) and `<name>.monitor.cedar` (monitor set; empty when every rule enforces). The platform's Java compiler (`privometry-platform/libs/policy`) must produce the same bytes, so the policy service and the edge never disagree about what a policy says. `go test ./internal/policy/compiler` fails if the files are stale.

## riskfeed

`manifest-hashes.json` (`privometry.manifesthashtest/v1`): MCP tool lists and the `tool_manifest_hash` each must give (riskfeed/v1 CHANGELOG draft.2), covering key order, extra fields, HTML characters, Unicode and control characters.

## signatures

`vectors.json` (`privometry.signaturetest/v1`): 23 cases, each an envelope, the key set to trust, the expected role and payload type, a verification time and `valid` or `invalid`.

- `check: artifact` verifies a signed document against `keyset-v2.json`.
- `check: keyset_update` verifies a key set rotation against the key set the device holds (`trust-root.json` or `keyset-v2.json`), including rollback.

Cases cover tampered payloads, relabeled payload types, wrong roles, unknown keys, a key ID that lies about its key, expired and not-yet-valid keys, a signature over the raw payload instead of PAE, unpadded base64, and the root rotation chain.

All files here are generated by `go run ./scripts/gen-conformance` from fixed seeds, so they are reproducible; CI fails if they drift. The keys are TEST KEYS with published seeds (`sha256("privometry-test-key:<role>:<name>")`). Never trust them anywhere else.

## redaction

`vectors.yaml` (`privometry.redactiontest/v1`): 38 cases of raw text and the expected output at the `redacted` or `hashed` level, under one context (home `/home/dev`, repo `/home/dev/work/api`) and a test hash key.

Rules, in order: private keys, URL credentials, known token formats (each with its own placeholder), authorization headers, URL query values, sensitive `NAME=value`, JSON fields and flags, emails (except `git@` SSH remotes), then paths. Paths inside the repo become `<repo>/...`; other paths under home become `~/<redacted_path>`; other users' homes become `/home/<user>`; system paths stay. Redaction is idempotent.

Inputs may contain `{{}}`, which runners remove before use, so sample tokens are never contiguous in the repository and secret scanners do not flag them.
